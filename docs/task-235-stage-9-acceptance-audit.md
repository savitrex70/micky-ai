## 4. Highest-priority blockers and security/privacy risks

### P1 — Expired clarification content is not proactively purged

The clarification table retains original_message and partial_operation. Expiry is enforced when a continuation is submitted, but src/rop/main.py startup recovery only invokes confirmation recovery. If a clarification expires and is abandoned, the temporary content can remain in the database after its advertised ten-minute lifetime. This is a concrete privacy/retention gap, not merely missing test evidence.

**Smallest safe correction:** add bounded transactional expiry cleanup at the existing startup/recovery boundary (and only if necessary at a safe request boundary), clear temporary content, fail safely on cleanup errors, and add expiry/restart/privacy-retention tests. Do not extend a challenge, change conversation ownership, or allow expired continuations to proceed.

### P1 — General personal-data export is absent

Confirmation records can be exported; conversations and workspace records cannot be exported through a comparable general-purpose user-controlled path. The contract defines export as part of persistence/user-control acceptance. This is therefore a functional acceptance blocker. Import is also absent; do not claim it exists or bundle an unsafe import implementation into the export fix.

### P1 — End-to-end evidence is incomplete even though CI is green

There is no recorded manual product walkthrough. Some workspaces' unit/parser/schema coverage is stronger than the complete end-to-end coverage for task/reminder mutation, overdue-after-restart, UI-to-database uncertain outcomes and retrieval-root security. A green aggregate test result must not be used to infer that these unverified workflows work.

### P1 — Database-dependent test execution is not fully accounted for

The CI job reports 218 skips and the workflow contains no PostgreSQL service or explicit ROP_TEST_DATABASE_URL. Tests that intentionally skip without an isolated database mean that “full suite green” is not the same as “every database/migration acceptance test executed.” Record the skip reasons and run the required migrations/integration tests with a dedicated disposable database.

### P2 — Retrieval adversarial/platform coverage is incomplete

The implementation has meaningful containment and resource guards, but the inspected test evidence does not establish every Windows network-drive/junction case or every resource ceiling. Avoid describing retrieval as security-accepted until adversarial tests demonstrate the boundaries on supported platforms and attempted network calls fail closed.

### P2 — Ordinary-use offline and resource claims are not yet evidenced

The UI serves local assets and provider-lockdown tests exist. This does not prove normal startup and the complete permitted Stage 9 workflow stay offline under actual runtime conditions. Resource limits being constants is not the same as measured resource acceptance.

## 6. Reproducible verification checklist still required

These are proposed steps. They were **not executed** as part of this documentation-only audit.

1. **Clean startup/offline:** on the target Windows environment, follow README.md from a clean checkout and fresh isolated database with no AI credentials configured. After installing dependencies, deny network access and start the application; check the documented local URL and health endpoint, load the interface, and run supported deterministic commands. Record attempted outbound connections or prove the test guard would fail on them.
2. **Conversations:** create two conversations; add successful turns to one; reload/reopen the page; inspect message order; rename and delete one; prove the other and all clinical sessions remain untouched. Simulate a lost response and verify the UI blocks blind replay until reconciliation.
3. **Clarification and workspace:** create a clarification, restart the API, restore it, try it against another conversation, consume it once, replay it, and test expired abandoned material cleanup. Exercise notes/tasks create/read/update/delete/complete with confirmation and idempotency checks.
4. **Reminders:** test normal, ambiguous and nonexistent local times; create/update/complete/delete reminders; move a due time into the past under a fixed test clock; restart with the same database and verify overdue reminders appear without silent loss or duplication.
5. **Confirmation/recovery:** test correct and wrong code, cancel, expiry, changed policy identity, repeated confirmation, conflicting idempotency key, established executor failure and process interruption after a mutation may have committed. Restart and reconcile by the original durable receipt/key; never retry an unknown outcome with a new key.
6. **Private retrieval:** authorize one temporary local folder; confirm allowed files are searchable and unsupported files are not; attempt symlink/junction escape, network share/mapped drive, inaccessible root, oversized file, directory/file-count bounds and path traversal. Confirm no network fetch is attempted.
7. **Privacy and clinical workflow:** inspect/export/delete confirmation records; verify current confirmation export omits secrets. Verify the absent conversation/workspace export is fixed before acceptance. In the separate clinical panel, create a clinical session, add observations, run the fully audited workflow, inspect the returned package and failure/inconsistency presentation, and confirm IDs/domains never cross.
8. **Database/regression gates:** run the required migration and PostgreSQL-specific suites against a disposable test database; report every skip reason. Rerun the full suite, Ruff and Black on the exact candidate SHA and link the completed CI run.

For each manual step, preserve the command or action, environment, tested commit SHA, observed output, and any deviations. Do not convert a test name or source-code inspection into a claimed manual pass.
